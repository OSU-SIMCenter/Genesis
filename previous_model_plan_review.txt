### 1. Critique of the Strategy

**✅ The Good: Memory Layout Management**

* **Why it works:** Taichi requires fields to be "placed" (`ti.root.place`) into the memory hierarchy (usually a Structure of Arrays) before any computation runs. By intercepting the dictionary generation via `get_particle_state_template()` *before* the `ti.Struct` is initialized, your subclass `ThermalMPMSolver` allows the `temp` field to be packed adjacent to `pos` and `vel`. This preserves cache locality, which is critical for performance.

**⚠️ The Trade-off: Kernel Splitting vs. Fusion**

* **Your Plan:** You propose separate `p2g_thermal` and `g2p_thermal` kernels called sequentially in `substep_pre_coupling`.
* **The Cost:** This requires the GPU to load particle data from VRAM twice per substep (once for momentum P2G, once for thermal P2G). In high-performance MPM, the simulation is almost always memory-bandwidth bound.
* **Verdict:** For a research prototype, **this is acceptable** and significantly cleaner to read. If you need to optimize later, you can copy the base `p2g` code and manually fuse the thermal logic into a single monolithic kernel in your subclass.

**❌ The Gap: Solver Integration**

* **The Problem:** Genesis is not designed for dependency injection. The `Simulator` class (in `genesis/engine/simulator.py`) explicitly imports and instantiates the `MPMSolver` class based on `MPMOptions`.


* **The Fix:** Even if you write `class ThermalMPMSolver(BaseMPMSolver)`, Genesis won't use it. You must either:
1. Modify `genesis/engine/simulator.py` to check for a new option (e.g., `use_thermal_solver=True`) and instantiate your class.
2. (Easier/Hackier) Name your file `mpm_solver.py` and replace the original file in the source tree, effectively "becoming" the default solver.
